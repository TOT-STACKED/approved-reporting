How Tech on Toast's stack works

Three places hold the data. Two automations move it. One dashboard reads it all — this is what talks to what, and where to look when something moves.

What we collect

Venue-side tech reviews come in through a Lovable-hosted form embedded in Webflow. Every submission writes one row in business_submissions, one row per tool picked in tech_stack_entries, and one row per rated product in nps_scores.

What we send out

Leads live in Airtable and get triaged by hand. Airtable automations ping the relevant partner in Slack (or Zenzap) as each lead moves from MAL through MQL, SQL, Closed Won and Closed Lost.

What each piece does

Webflow
Hosts the public tech-check landing page at techontoast.community. Just an iframe embed — nothing else lives here.
Lovable form
The React app the operator actually fills in. Walks them through picking tools per category and (optionally, for now) rating each 0–10.
Lovable Supabase
Owns three tables. business_submissions — one row per operator. tech_stack_entries — one row per tool picked. nps_scores — one row per rated product. Also runs two edge functions: stack-review generates the AI review and saves it to business_submissions.recommendations; stackcollect-webhook writes the NPS rows.
Resend
Emails the finished AI review to the operator. Fires once stack-review completes.
/tech-check
The insights page on Approved Reporting. Reads Supabase live (no caching). Category cards, per-venue drilldown with per-tool NPS, and Markdown download of every operator's report.

What each piece does

Airtable
Master Lead Sheet is the source of truth for leads. Five multi-select columns hold partner names per stage (MAL, MQL, SQL, Closed Won, Closed Lost). One lead can be at different stages for different partners.
Airtable automation
Fires when any stage column changes. Reads the "…Notified" tracking columns to see which partners are genuinely new to that stage, then routes: Slack partners get pinged in their own channel, Zenzap goes via HTTP to the Zenzap API. Writes back to "…Notified" so no partner is pinged twice for the same stage.
Slack (per-partner)
Every partner has a dedicated channel. Channel IDs live in the Slack_Data table on Airtable. If an ID is missing the automation logs the miss but doesn't block the others.
Zenzap
Only the Zenzap partner is routed here — their alerts go to the "approved leads" topic via HMAC-signed API call. Everyone else stays on Slack.
Approved Reporting
Next.js app on Netlify at approvedreporting.netlify.app. Three lead-facing views: / (main dashboard with SOS League), /partners/:slug (internal team, gated by dashboard password), /p/:token (partner-facing, private URL per partner, contact details gated behind MQL).
Feedback API
Two endpoints, one per surface (internal or token). Both write a row to lead_feedback on Lovable Supabase and post a formatted card to Slack #lead-feedback. Source is tagged internal vs the partner's token tail so we can tell them apart later.

What each piece does

stackcollect-webhook
Edge function on Lovable Supabase. Called from the form when the operator submits with any product ratings. Writes one nps_scores row per rated product, keyed by submission_id so the score attaches cleanly to the venue.
Watchdog (48h)
Scheduled Lovable job — checks MAX(created_at) on nps_scores every 48 hours. If nothing's landed since the last run, posts a warning to Slack. Catches the June-style silent outages within two days instead of a month.
Staleness banner
Client-side check on the Approved Reporting NPS section. If the latest score is more than 7 days old, an amber banner appears at the top of the NPS panel — visible to anyone opening the dashboard. 30+ days it goes red.
Two false-positive modes
Not every watchdog fire is a bug. The alert triggers on either a broken writer (real outage) or a legit low-activity 48h window where no operator rated anything. First check the webhook logs — if they're clean, it's the second case, no action needed.

Debug

If something's off, look here first

Six patterns cover most of what goes sideways. Start with the "first place" column before opening a ticket with Lovable. The Owner column is a suggestion — swap in the real name from your team.

SymptomFirst place to lookOwner
Dashboard shows an old lead as "latest" Airtable — has anyone triaged recent MALs into MQL / SQL? The dashboard reads genuine partner-tagged activity, not raw form arrivals. TOT team
Partner didn't get their Slack alert Airtable Slack_Data — is there a channel ID for that partner? Then check the automation's run history for that specific record. TOT team
NPS score isn't showing on a tech check Lovable Supabase nps_scores — is there a row for that venue? Most of the time the operator just skipped the sliders; roughly half of new submissions still do. Lovable

Partner sees "Access Denied" on their URL Netlify environment variables — is their token in PARTNER_TOKENS? Redeploy after any edit. Chris

Onboarding

Adding a new partner

Every new partner touches three systems: Airtable (they need to exist as a taggable option), Netlify (they need a private URL token), and the portal code (they need a vendor-name alias so tech-stack matching resolves). Miss any one and something silently fails.

  1. Add the partner to Airtable stage columns

    Open the Master Lead Sheet. On each of the five stage columns (MAL, MQL, SQL, Closed Won, Closed Lost) add the partner's exact display name as a new multi-select option. Case and spelling matter — everything downstream normalises off this.

  2. Give them a Slack channel + record it

    Create their private Slack channel, invite Chris, then add one row to the Slack_Data table on Airtable — partner name (exact match) and the channel ID. If the channel ID is missing, the automation quietly skips them.

  3. Generate a private URL token

    URL-safe 32-character random string. Paste this in a terminal on any Mac:

    node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"

  4. Add the token to Netlify

    Netlify → Site config → Environment variables → PARTNER_TOKENS. It's a JSON object; add one entry inside the braces (don't forget the trailing comma on the previous entry):

    "<the-token>": "<partner-slug>"

    Slug is lower-case with hyphens for spaces — same as the URL you'd expect: sevenrooms, seven-rooms, clearcourse. Save, then trigger a Netlify redeploy.

  5. Add a vendor alias (for tech-stack matching)

    In src/lib/stackcollect.ts, add an entry to PARTNER_VENDOR_ALIASES. Key is the slug you used above; values are every case-insensitive substring their product might appear as in operator reviews:

    'sevenrooms': ['sevenrooms', 'seven rooms', '7rooms'],

    Commit, push, Netlify auto-deploys. Without this the partner still gets Slack pings for their leads, but their NPS scores won't attach to them on the tech-check drilldown.

The private URL to share: https://approvedreporting.netlify.app/p/<the-token>. Test it in an incognito window before sending it to the partner — should land on their dashboard, not "Access Denied".

Three places hold the data. Lovable (venues + NPS), Airtable (leads + partners), Netlify (the portal that reads both). If you know which one owns the thing you're chasing, you're already halfway to the fix.
